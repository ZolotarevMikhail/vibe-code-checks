# Разбор: бот, который отдал свои ключи

**Вход:** два мёртвых Telegram-бота, репозиторий с вайбкод-ботом (файлы + `.env`, всё закоммичено), история гита.
**Задача:** сказать, что именно утекло, объяснить, что из этого следует, и убрать секреты из проекта навсегда.
**Проверка:** живые команды против репо заказчика (`git show`, скан истории, запуск бота) — то же самое делается над любым проектом, который заказчик держал в открытом репозитории. Все токены в демо вымышленные.

---

## Резюме для владельца

Утечка не гипотеза, а факт: токен бота и ключ магазина лежат и в коде, и в отдельном файле `.env`, и в истории гита. Папка «код на GitHub, чтобы смотреть с телефона» — это и есть место слива: любой посетитель страницы видел все ключи. Боты, вероятно, замолчали не из-за оплаты сервера: с живым токеном чужой человек может увести управление ботом, а с ключом магазина — ходить в него данными от вашего имени.

Хорошая новость: ремонт небольшой. Плохая: ремонт начинается не с кода, а с перевыпуска ключей. Пока ключи живы, чистка репозитория ничего не защищает — чужие скрипты и архивы хранят их годами.

## Как проверял

Три шага. Сначала скан: поиск всех строк вида «токен/ключ» по файлам проекта и по всей истории гита (`git log -p --all`) — так видно и то, что утекло сейчас, и то, что утекло месяцами раньше. Потом запуск бота: важно, что печатается в лог при старте. Дальше — чтение кода: где ключ спрятан, кто его видит и что происходит с логами.

Что увидел в живом прогоне: `.env` внутри первого же коммита; оба ключа читаются из истории одной командой `git show`; при запуске бот печатает все ключи в лог целиком.

## Находки

### Критично

**1. Токен бот-платформы прямо в коде.**
`TELEGRAM_TOKEN = "7912…"` первой строкой файла. Весь код лежал в публичном репо: у каждого, кто однажды открыл страницу, остался доступ к управлению ботами. Это объясняет и «висели мёртвые»: чужой человек мог перенастроить ботов, остановить их или занять токен другим скриптом.

**2. `.env` с ключами закоммичен, `.gitignore` отсутствует.**
Файл `.env` придуман, чтобы секреты не попадали в репозиторий, но без записи в `.gitignore` git его просто берёт, как любой другой. В коммит ушло всё: телефонная книга всех ключей проекта.

**3. Удаление файла из гита ничего не чистило бы.**
У заказчика типичный план «удалю .env и запушу заново». Это не работает: история хранит файлы навсегда, `git show HEAD~1:.env` отдаёт содержимое и после удаления. Чистка истории возможна, но настоящая защита одна — перевыпуск ключей.

### Важно

**4. Ключ магазина-источника в том же файле.**
`SHOP_API_TOKEN` живёт рядом, с той же судьбой. Это ключ к чужому сервису от имени заказчика: чьи-то запросы выглядят как ваши.

**5. Ключи печатаются в лог при каждом старте.**
`print("конфигурация:", …)` вываливает все значения целиком — в живом прогоне все четыре ключа оказались в консоли. Логи уходят на сервер, в мониторинг, в скриншоты техподдержки: отдельный тихий канал утечки.

### Мелочи

**6. Мёртвый `.env` в коде продублирован.**
Файл читает и код, и `.env`: два места правды. Если правится одно, бот работает с другим. Так рождаются «бот не работает, хотя я поправил файл».

**7. Комментарий «не потеряй» вместо защиты.**
Инструкция держателю токена защищает хуже, чем механизм: у кого код — у того и токен, как ни пиши.

## Что было утрачено, если коротко

| Что утекло | Где жило | Что можно было сделать с ключом |
|---|---|---|
| Токен бота | код + .env + история гита | управлять ботами, читать переписку |
| Ключ магазина | код + .env + история гита | запросы от имени заказчика |
| Ид таблицы | код (сам по себе не ключ) | знает, где лежат данные |
| Ключ Google API | код + .env | платные запросы от имени заказчика |

## Что исправлено

Правки — в `исправленная-версия/`. Смысловые:

- в коде нет ни одного ключа: всё приходит из окружения; если `.env` пуст, бот честно скажет «не заданы переменные: …» и остановится, а не завалится с полутонной трейса;
- в проекте появился `.gitignore` (`.env`, логи, кэш python) и `.env.example` — образец с пустыми значениями, по которому новый человек собирает конфигурацию, не видя настоящих ключей;
- логи больше не печатают секреты: только «конфигурация загружена, значение в лог не печатаю» — в живом прогоне видно разницу сразу;
- запросы к внешнему сервису — с таймаутом.

Живой прогон исправленной версии: без `.env` — понятное объяснение и остановка; с заполненным окружением — «конфигурация загружена: 3 ключей», ни одного значения в выводе; `git add` не берёт `.env` (проверено командой `git check-ignore`). Отдельно: сеть в прогоне не предмет разбора, домен источника вымышленный.

Первым делом заказчику: перевыпустить токен бота у BotFather и ключи в кабинете магазина. Инструкция по шагам — в `исправленная-версия/README.md`.

## Чек-лист: как самому заметить такое

1. Найди файл `.env` рядом с кодом. Есть `.gitignore` с записью `.env`? Нет записи — ключи уже в репо, проверяй `git log -p --all | grep -i token`.
2. Открой `README.md` проекта глазами чужого человека. Если по тексту можно собрать конфигурацию — она уже собрана.
3. Запусти проект локально и посмотри первые строки лога. Видно все значения ключей — считай, что ключи теперь у каждого, кто видел лог.
4. Проверь файл кода на строки вида `TOKEN = "..."`. Константа с ключом — верный признак вайбкода, который надо перенести в окружение.
5. Помни порядок: ключи перевыпустить, потом чистить репозиторий. В обратном порядке не работает.
