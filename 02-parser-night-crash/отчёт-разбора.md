# Разбор: парсер, который падал по ночам

**Вход:** вайбкод-парсер цен конкурента (`исходник-с-ошибками/парсер.py`) + лог ночных падений.
**Задача:** объяснить, почему ночью всё падает и почему утром CSV пустой, и починить.
**Проверка:** источник в демо — стенд `стенд/mock_api.py`, который ведёт себя как настоящий API без повторов: первый запрос каждой категории отвечает «429» (лимит), у категории 105 второй запрос — «500» (сбой). У этого стенда ровно те повадки, из-за которых у заказчика встало.

---

## Резюме для владельца

Парсер не переживает ни единой ошибки источника. Источник сам по себе живой, у любого нормального API бывают лимитные ответы «429» и разовые «500». Парсер на такое не рассчитан: любой сбой — падение всего процесса. Хуже того: файл результата открывается на перезапись в самом начале, поэтому при падении в середине ночи утренний CSV пустой. Пусто не потому, что «данные не собрались». Собрали, а потом стёрли.

Разовый сбой источника и потеря накопленных данных — это две разные проблемы, и обе чинятся за считанные строки кода. В ночной лог заказчика падение не попало потому, что логов у парсера, по сути, нет.

## Как проверял

Прогнал парсер по назначению против стенда и сравнил поведение «до» и «после» на тех же ответах источника. Отдельно прочитал код: откуда берётся каждый сбой и что происходит с файлом, если процесс умирает в середине. Заказчик видел в браузере, что источник отвечает, — да, отвечает, только не тем ответом, который ждёт вайбкод.

## Находки

### Критично

**1. Одна ошибка источника валит весь сбор.**
Код даже не спрашивает, успешен ли ответ: `resp.json()` выполняется на любом коде состояния. При «429» источник возвращает JSON с полем `error`, у такого объекта нет `items`, и парсера уже не спасти: `KeyError: 'items'`. Ловится живым прогоном: крэш на первом же запросе.

**2. Перед запросами файл открывается на перезапись.**
`open(..., "w")` и заголовок записываются в начале скрипта. Всё, что собрано до падения, затирается навсегда. В прогоне файл с данными предыдущего прогона остался с одной строчкой заголовка. У заказчика это и есть «утром файл пустой».

**3. Запросы без таймаута.**
`requests.get(url)` без `timeout` ждёт ответа вечно. Источник, который молчит (а такое бывает: обрыв сети, затык на стороне сервера), подвешивает процесс. Расписание запускает парсер заново поверх зависшего — в логе заказчика это и видно: «предыдущий запуск не завершился».

### Важно

**4. Молчаливые потери строк.**
Каждая строка данных пишется в `try/except Exception: pass`. Строка с любым сюрпризом тихо пропадает, и никто об этом не узнает: ни счётчиков, ни лога. Причём падение скрипта из-за пропущенной строки невозможно — это «спокойный» способ терять данные месяцами.

**5. Один «странный» товар ломает всю выгрузку.**
Цена читается жёстко: `item['price']`. У источника нашёлся товар без цены («Пояс #20, цена не задана») — с ним весь прогон падает на второй странице второй категории. Один товар, ни цены, ни названия — а ночной сбор умер.

**6. Запрашивает без пауз.**
Страницы и категории идут сплошным циклом. Чем безжалостнее пачка запросов, тем раньше источник вернёт «429» и тем вернее парсер упадёт (находка 1). Вежливая пауза в полсекунды дешевле, чем ночной крэш.

### Мелочи

**7. Токен зашит в коде.** `API_TOKEN = "demo-token-12345"` — файл уходит по почте, в архивах, в гит. Токен не должен жить в коде. (Подробнее — соседний разбор №3 «Ключи в коде».)

**8. Кодировка CSV не указана.** `open(..., "w")` пишет в кодировке, назначенной конкретной машиной: на одной получится utf-8, на другой cp1251 — файл, полученный с чужого компьютера, откроется в Excel кракозябрами. Правильно писать явным utf-8-sig: русские CSV в Excel открываются сразу.

**9. Лог не атрибутируем.** Ни метки времени, ни категории, ни уровня важности. В traceback видно только строку кода. Ночное падение без времени и места не починить — оно просто пропадёт из ночи.

## Что исправлено

Правки — в `исправленная-версия/парсер.py`. Смысловые:

- любые сбойные ответы (429/5xx/обрыв сети) дают повтор с паузой, конечным числом попыток и растущим ожиданием: 2, 4, 8, 8 секунд; таймаут одного запроса — 20 с;
- категории независимы: если одна в конце концов не собралась, остальные сохраняются, ошибка видна в логе, а файл прошлого дня никто не трогает (записывается только собранное целиком и одним шагом «подмены» файла);
- товар без цены пропускается с записью в лог, счётчик пропущенных виден;
- пауза полсекунды между запросами — источник не провоцируется;
- токен берётся из окружения, в коде его нет; без токена парсер напомнит об этом в логе, а не молча соберёт непонятно что;
- у каждого события лога есть время и уровень («info» собрано, «warn» пережили повтором, «error» не собрано);
- выходной код: 0 — всё собрано, 2 — есть невнятности; по нему расписание отличит ночной крэш от успешного прогона.

Живой прогон исправленной версии на том же стенде: 74 строки данных, одна категория пережила «500» на повторе, товар без цены пропущен и посчитан, файл обновлён, код выхода 0. Прогон повторён второй раз для чистоты — тот же результат.

## Чек-лист: как самому заметить такое

1. Открой CSV парсера перед ночной гонкой: если файл меняется «в начале процесса» — любое ночное падение сотрёт данные.
2. Найди в коде `except` — если рядом с ним «pass», данные пропадают молча и навсегда.
3. Попроси нейросеть «выбросить сеть на минуту» — подними стенд, который отвечает 429/500, и погоняй парсер у себя. Если падает — у нас то, что и у заказчика.
4. Посмотри, есть ли у запросов таймауты и повторы. Их отсутствие — не «экономия строк», а гарантированный ночной сюрприз.
5. Прочитай лог ночных падений построчным поиском времени. Нет времени — лог не читаем, падение не найдёшь.
