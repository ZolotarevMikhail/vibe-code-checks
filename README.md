# Проверка чужого вайб-кода — серия кейсов

Три разбора вайбкод-проектов: что нейросеть собрала заказчику, где это врёт или падает, и как починено. Каждый кейс — учебный по мотивам реальных ТЗ с биржи; данные условные, а ошибки и процесс проверки настоящие. Сломанная и исправленная версии лежат рядом: обе можно открыть и проверить самому, команды для этого есть в README каждого кейса.

## Кейсы

| Кейс | Суть | Где смотреть |
|---|---|---|
| [№1 — Числа в дашборде не сходятся](01-dashboard-numbers/) | Выручка, заказы и средний чек на «красивом» дашборде считались неверно: возвраты прибавлялись к выручке, штуки выдавались за заказы, плитки не пересчитывались в фильтрах | Сверка цифр с выгрузкой: 5 из 5 показателей совпали после правки |
| [№2 — Парсер падает ночью](02-parser-night-crash/) | Одна ошибка источника (429/500) валила весь сбор, а результатный файл открывался на перезапись в начале: утром CSV пустой, хотя данные собрались | Стенд-имитация API идёт в комплекте: до/после на одних и тех же ответах |
| [№3 — Ключи в коде и .env](03-keys-in-code/) | Токен бота и ключ магазина лежали в коде, в `.env` и в истории гита открытого репозитория; бот печатал ключи в лог при каждом старте | Команды находят утечку в этом же демо-репо за 2–3 минуты |

## Общий процесс проверки

1. Сверка результата с первоисточником (выгрузка кабинета, отвечающий стенд, история гита) — независимо, другим инструментом.
2. Чтение кода: по каждой цифре/сбойной точке — как считается и откуда берётся.
3. Живые прогоны: поведение «до» и «после» на одних и тех же входных данных.
4. Отчёт владельцу: находки по приоритетам (критично/важно/мелочи), таблица «до/после», как самому заметить такое.

## Как смотреть

Каждая папка кейса самодостаточна: `README.md` — оглавление и команды; `отчёт-разбора.md` — главный документ; `исходник-с-ошибками/` и `исправленная-версия/` — работающие версии. Номера кейсов — порядок серии, а не рейтинг.
